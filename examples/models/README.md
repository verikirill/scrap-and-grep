# Сравнение моделей

Задание требует, чтобы модель менялась без существенной переработки и основной сценарий сохранялся на другой модели с нужными возможностями. Здесь один сценарий прогнан на нескольких моделях. Профили, неделя примеров (25 сентября - 2 октября 2026 года, снимок [data/samples](../../data/samples/articles.jsonl)) и граф сборки одинаковые. Чтобы сменить модель, меняли только переменные `RADAR_LLM_MODEL`, `RADAR_LLM_BASE_URL` и `RADAR_LLM_REASONING`, код не трогали.

Модели:
- `gpt-oss:120b` - основная, из списка финала; здесь она в облаке Ollama, только для проверки сценария: в финальном решении облако запрещено, локально её поднимает `docker-compose.vllm.yml` на карте 80 ГБ;
- `gpt-oss:20b`, `gemma4:31b` и `nemotron-3-nano:30b` - облако Ollama, ближайшие по классу к Qwen3.6 35B-A3B из задания, которой в облаке Ollama нет;
- `qwen3.5:9b` - локально в стеке, на видеокарте 8 ГБ; её нет в списке финала, это вариант для слабой карты;
- автономный режим без модели.

Моделей Яндекса здесь нет: ключа Yandex AI Studio у команды пока нет, путь через OpenAI-совместимый API закрыт тестом с подменённым сервером.

Каждая модель собирала выпуски с пустым кешем ответов, в отдельной базе Valkey, поэтому время сборки сравнимо. Обе `gpt-oss` работали с уровнем рассуждений `low`: выключить их рассуждения нельзя. Остальные модели работали без рассуждений. Сырые ответы лежат в `<модель>.json` и `<модель>.dataset.json`, выпуски в Markdown - в папке модели.

## Что видно

Сценарий сохраняется на каждой модели: выпуск собран целиком, с разделами «Атаки» и «Уязвимости», карточками, приоритетом по правилу датасета, сверкой с CISA KEV и БДУ и проверкой по тексту. Ни у одной модели в итоговых прогонах нет откатов на автономный режим.

Отбор держится на поиске. Даже без модели 13 из 20 записей те же, что у `gpt-oss:120b`, а модели расходятся с ней в суждении о 3-11 записях у порога. Два прогона самой `gpt-oss:120b` при температуре 0 совпадают в 18 записях из 20, так что расхождение в 2 записи - это шум облака.

Признаки руководства шумят ещё сильнее: у `gpt-oss:120b` в двух прогонах 17 и 26 из 32. Разницу между моделями в этой колонке меньше 10 мы не считаем различием. Тип записи совпал с датасетом у всех, приоритет - в 4 из 7 у всех моделей и в 3 из 7 без модели.

`gemma4:31b` ближе всех к основной модели (17 из 20) и быстрее её. Это запасной вариант в облаке.

`gpt-oss:20b` в облаке Ollama вдвое медленнее старшей. Почти всё в выпуске она назвала уязвимостями (18 из 20), а с основной моделью совпала только в 12 записях.

`nemotron-3-nano:30b` сама инструмент не вызывает: все 30 номеров проверил граф, поэтому справка из баз в выпуске всё равно есть. Проверка убрала из её карточек 8 полей, которых нет в статьях. Руководству она ставит по 6-7 признаков на запись, в датасете это 33 лишних.

`qwen3.5:9b` работает в стеке, на видеокарте 8 ГБ, и собирает выпуск без откатов за 165 секунд. Высокий приоритет у неё получили 2 уязвимости против 5-7 у облачных моделей, и инструмент она вызывает реже: 12 раз против 18-22.

`gpt-oss:120b` остаётся основной для примеров: она в списке финала, и на ней собраны все примеры. По умолчанию стек пишет локальной Qwen3.6 35B-A3B; ни её, ни `gpt-oss:120b` локально здесь нет: на карте 12 ГБ они не помещаются. По этим прогонам `gemma4:31b` ей не уступает, и если основная модель станет недоступна, запасную включает одна переменная.

### Как облако отказывало

В первом прогоне `nemotron-3-nano:30b` облако Ollama отвечало `429 too many concurrent requests`, и после трёх отказов подряд предохранитель переводил шаг в автономный режим. Модель оценила 2 кандидата из 60 и не написала ни одного текста. Выпуск всё равно собрался, с плашкой о том, что модель была недоступна.

После этого стек на 429 ждёт и спрашивает снова: шесть повторов с паузой от 2 до 30 секунд, всего около полутора минут, и только потом считает вызов отказом. Во втором прогоне повторы были короче, около 14 секунд, и модель оценила 30 из 60. В третьем облако не отказывало ни разу, в таблице он и стоит. Повтор `gpt-oss:120b` тоже собран на стеке с этой правкой, остальные прогоны - до неё.

## Как повторить

Локальная модель, например Qwen3.6 35B-A3B из списка финала: стек запущен с ней (README, «Быстрый запуск»), дальше одна команда из корня репозитория:

```bash
backend/scripts/measure_model.sh qwen3.6-35b-a3b
uv run scripts/model_report.py examples/models
```

Скрипт сам очищает кеш ответов и пишет рядом с выпусками `qwen3.6-35b-a3b.hardware.json`: карту, драйвер, пиковую видеопамять, процессор, память и версию Ollama. Токены на вход и выход за выпуск и скорость записи ответа лежат в `qwen3.6-35b-a3b.json`, в поле `usage` у каждого выпуска.

Облачные прогоны выше сделаны так, модель задавалась прямо в команде:

```bash
docker exec -i radar-api-3 sh -c 'cat > /tmp/dataset.json' < docs/task/dataset_v4.0.json
docker exec -i -e RADAR_CACHE_URL=redis://valkey:6379/7 -e RADAR_LLM_MODEL=gemma4:31b \
    -e RADAR_LLM_REASONING=off radar-api-3 python - < backend/scripts/model_compare.py
docker exec radar-api-3 cat /tmp/model_compare.json > examples/models/gemma4-31b.json
docker exec -i -e RADAR_CACHE_URL=redis://valkey:6379/7 -e RADAR_LLM_MODEL=gemma4:31b \
    -e RADAR_LLM_REASONING=off radar-api-3 python - < backend/scripts/dataset_run.py
docker exec radar-api-3 cat /tmp/dataset_run.json > examples/models/gemma4-31b.dataset.json
uv run scripts/model_report.py examples/models
```

Перед каждой моделью база кеша очищается: `docker exec radar-valkey-1 valkey-cli -n 7 flushdb`. В Git Bash перед командами с `/tmp` нужен `MSYS_NO_PATHCONV=1`.
